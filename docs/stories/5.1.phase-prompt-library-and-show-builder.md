# Story 5.1: Phase Prompt Library and Show Builder

## Status
- Draft (Future — do not implement until all hardware and core software is verified on stage; see Dev Notes)

## Story
As a Magician-Developer, I want a library of named, self-describing phase prompt documents that I can compose into a show of any length and order through a dashboard, so that I can build different routines (1-phase warm-up sets through 6+ phase full shows) without touching code or core config.

## Background / Vision
The planned five-phase Effie routine (inert doll → one phrase subtly wrong → sentience and perception → anger and backstory → the presence flees, doll is inert again) is one *show*, not the only show. Phases should be reusable, named building blocks:

- Each phase prompt document carries **metadata at the top**: a human-readable name describing its style/tone (e.g. "Inert Doll", "The Stirring", "Perception", "Fury", "Departure"), and the **voice trigger phrase** that switches the performance *into* that phase.
- The settings dashboard shows the library of phase documents. The performer picks any number of them (3 for a club set, 6 for a full theater show), **drags them into the show layout, and orders them freely**.
- New phase documents are written inside the dashboard, starting from a **template** that scaffolds the metadata header and prompt body.
- At showtime, the application loads the composed show; the active phase's prompt drives the LLM. The code **preloads the next phase's trigger phrase** and listens for it in each transcript; on match, it swaps the model prompt to the next phase. (F11 long-press remains as the silent/manual fallback.)

## Acceptance Criteria
1. Phase prompt documents have a structured metadata header (YAML front matter) with at minimum: `name` (style/tone label), `trigger` (spoken phrase that activates this phase). The body below the header is the prompt text, as today.
2. A `prompts/library/` directory holds all phase documents; documents are self-contained and order-independent (no phase numbers baked into filenames).
3. The show composition (which documents, in which order) lives in `config/settings.yaml` — e.g. `show: ["inert-doll", "perception", "departure"]` — extending the existing performer-settings file from the Epic 5 groundwork. `phases: N` simple mode remains as the degenerate case (persona only).
4. Shows of any length are supported (1 to 6+); the prompt loader resolves the Nth phase from the composed show, not from `phase_N_prompt.txt` filenames.
5. On each transcript, the application checks for the *next* phase's `trigger` phrase (preloaded at phase entry, matched case-insensitively and tolerant of transcription noise); on match it advances the phase and swaps the prompt. Manual advance (F11 long-press) still works.
6. The dashboard (separate story) can list, create (from template), edit, and arrange phase documents, writing only `prompts/library/` and `settings.yaml` — never `config.yaml` or code.
7. A starter template document exists with the metadata header stubbed and guidance comments in the body.
8. Backward compatibility: with no `show:` key in settings, behavior is exactly the current one (`phases: N` → `phase_N_prompt.txt` files, or persona-only when N=1).

## Dev Notes
- **Sequencing**: explicitly deferred. Order of operations is (1) all hardware working, (2) all current software verified live, (3) one/two-phase warm-up routine performed publicly, (4) then this.
- **Groundwork already in place** (2026-06-12): `config/settings.yaml` exists as the performer-settings overlay with `phases:`; the prompt loader already supports persona-only mode; phase tools are gated off in single-phase shows. This story extends that layer rather than inventing a new one.
- **Trigger matching caution**: trigger phrases pass through the same transcription as everything else — choose phrases that are phonetically distinct from ordinary patter, and normalize (lowercase, strip punctuation) before matching. False positives advance the show irreversibly; consider requiring the match at sentence start, or a confirmation window. The performer-mistake recovery concern that kept response generation in a single model (2026-06-12 decision) applies here too.
- **Why front matter**: keeps each document self-contained and dashboard-editable; the code never needs a registry besides the directory listing.
